# Ballast Infrastructure & Worker Deployment Guide

This document outlines the deployment architecture for Ballast and details how to deploy and configure the standalone worker on **Render** (supporting both Render Free Tier Web Service and paid Background Worker).

---

## Architecture Overview

Ballast is split into two complementary environments:

1. **Frontend & API (Vercel)**:
   * Hosts the Next.js web application and serverless route handlers.
   * Handles user authentication, dashboard UI, and enqueuing jobs to BullMQ (`/api/briefs/enqueue`, `/api/briefs/[id]/regenerate`, `/api/actions/[id]/approve`).
   * **Does not** execute long-running pipeline worker jobs directly.
   * On dashboard load or when enqueuing a job, Next.js sends an async ping to the worker's `/health` endpoint to ensure the worker is awake (if running on Render Free Tier).

2. **Worker Service (Render)**:
   * Hosts the BullMQ worker (`src/worker.ts` via `npm run worker`).
   * Consumes jobs from Redis (`ballast-briefs` and `ballast-actions`).
   * Executes multi-stage document retrieval, multi-provider LLM calls (writer/critic), verification, citation generation, action drafts, and external action executions.
   * Runs an autonomous 60-second cron scheduler loop (`cron-parser`) querying and triggering enabled schedules, guarded with row-level atomic locks against double-firing.
   * Listens on `PORT` (default 10000) providing `/health` and `/wake` endpoints for Render health checks and wake-up pings.
   * Emits a 60-second heartbeat log for liveness observability.

Both services connect to the **same PostgreSQL database** (`DATABASE_URL`) and the **same Redis queue** (`REDIS_URL`).

## Render Free Tier vs. Paid Worker

Render treats free and paid services differently:

| Feature | Render Free Tier (Web Service) | Render Starter ($7/mo Background Worker) |
| :--- | :--- | :--- |
| **Service Type** | `type: web` | `type: worker` |
| **Cost** | $0/month | $7/month |
| **Sleep Behavior** | Spins down after 15 minutes of inactivity | Always on, never sleeps |
| **Wakeup Mechanism** | Wakes up automatically when an HTTP request hits its URL (takes ~30-50s cold start) | N/A (runs continuously) |
| **Public URL** | Yes (e.g. `https://ballast-worker.onrender.com`) | No public URL |
| **Vercel Config Needed** | **Yes**: Add `WORKER_URL` on Vercel | **No**: No URL needed |

> [!TIP]
> Ballast is built to support **both options out of the box**!
> If you deploy on Render Free Tier as a Web Service, Ballast's built-in HTTP server will handle health checks and wake-ups automatically.

## Deployment Steps on Render (Action for James)

### Option A: Deploy via Render Blueprint (One-Click)

1. Log into your [Render Dashboard](https://dashboard.render.com/).
2. Click **New +** in the top navigation bar and select **Blueprint**.
3. Connect your GitHub repository (`Jamesuchechi/Ballast`) and select the active branch.
4. Render will detect [`render.yaml`](file:///home/jamesuchechi/Projects/Ballast/render.yaml) which is pre-configured for the **Free Tier**:
   * **Service Name**: `ballast-worker`
   * **Service Type**: `Web Service`
   * **Plan**: `Free`
   * **Runtime**: `Node`
   * **Build Command**: `npm install && npm run db:migrate`
   * **Start Command**: `npm run worker`
   * **Health Check Path**: `/health`
5. Click **Apply**.
6. Under the service's **Environment** tab, populate your secret environment variables (see table below).
7. Copy your worker's public Render URL (e.g. `https://ballast-worker.onrender.com`).

---

### Option B: Manual Service Creation (Free Web Service)

1. Go to the [Render Dashboard](https://dashboard.render.com/).
2. Click **New +** -> **Web Service**.
3. Connect the `Ballast` repository.
4. Configure the service:
   * **Name**: `ballast-worker`
   * **Region**: Choose the region closest to your database (e.g., `Oregon (US West)`).
   * **Branch**: `main`
   * **Runtime**: `Node`
   * **Build Command**: `npm install && npm run db:migrate`
   * **Start Command**: `npm run worker`
   * **Plan**: `Free`
   * **Health Check Path**: `/health`
5. Add the Environment Variables listed in the table below.
6. Click **Create Web Service**.
7. Copy the public URL generated by Render (e.g. `https://ballast-worker.onrender.com`).

## Environment Variables Configuration

### Do you need to add URLs?

1. **On Vercel (Frontend / API)**:
   * **YES, if using Render Free Tier**: Add `WORKER_URL`.
     ```env
     WORKER_URL=https://ballast-worker.onrender.com
     ```
     *When set, the frontend and API routes automatically send a wake-up ping to `/health` whenever the dashboard opens or a job is enqueued, waking the worker up from free-tier sleep.*
   * **If using paid always-on worker**: Not strictly required, as the worker never sleeps.

2. **On Render (Worker)**:
   * **NO, you do NOT need Vercel's URL on Render.**
   * The worker communicates entirely through Redis and PostgreSQL. It never needs to make HTTP requests back to Vercel.

### Required Environment Variables on Render

Set the following environment variables in your Render service:

| Variable | Description | Example / Source |
| :--- | :--- | :--- |
| `NODE_ENV` | Environment mode | `production` |
| `PORT` | HTTP port for health & wake endpoints | `10000` (Render sets this automatically) |
| `DATABASE_URL` | PostgreSQL connection string | Same database URI used on Vercel (Neon Postgres) |
| `REDIS_URL` | Redis URI for BullMQ queues | Same Redis connection used on Vercel (Upstash Redis) |
| `UPSTASH_REDIS_URL` | *(Optional)* Upstash TLS URI | Alternative to `REDIS_URL` if using Upstash directly |
| `GEMINI_API_KEY` | Google Gemini API key | Same key as on Vercel |
| `GROQ_API_KEY` | Groq Cloud API key | Same key as on Vercel |
| `MISTRAL_API_KEY` | Mistral AI API key | Same key as on Vercel |
| `OPENROUTER_API_KEY`| OpenRouter API key | Same key as on Vercel |

### Optional Cloud Object Storage (Cloudflare R2 / AWS S3)

By default, Ballast automatically uses local filesystem storage (`.storage/`). If configured, Ballast will seamlessly switch to S3/R2 cloud storage for persistent PDF storage across worker restarts and redeploys:

| Variable | Description | Example |
| :--- | :--- | :--- |
| `R2_BUCKET` | Cloudflare R2 or S3 bucket name | `ballast-artifacts` |
| `R2_ACCOUNT_ID` | Cloudflare account ID (used to construct R2 endpoint) | `a1b2c3d4e5f6...` |
| `R2_ACCESS_KEY_ID` | R2 or AWS access key ID | `AKIA...` |
| `R2_SECRET_ACCESS_KEY` | R2 or AWS secret access key | `secret...` |
| `S3_ENDPOINT` | *(Optional)* Custom S3 endpoint if not using R2 | `https://s3.us-east-1.amazonaws.com` |
| `S3_REGION` | *(Optional)* S3 region | `auto` (for R2) or `us-east-1` |

> [!NOTE]
> If these variables are omitted, Ballast continues running with 100% functionality using the local filesystem driver.

### Optional Transactional Email Delivery (Resend)

By default, Ballast creates in-app notifications and logs simulated email dispatches cleanly when `RESEND_API_KEY` is not provided. When you add a Resend API key to your Render worker, Ballast automatically sends transactional emails when automated briefs are published or fail:

| Variable | Description | Example / Default |
| :--- | :--- | :--- |
| `RESEND_API_KEY` | Resend API key (`re_...`) | `re_123456789...` |
| `EMAIL_FROM` | *(Optional)* Sender address | `Ballast <briefs@yourdomain.com>` (defaults to `Ballast <onboarding@resend.dev>`) |
| `APP_URL` | *(Optional)* Web app base URL for notification links | `https://ballast.vercel.app` |

> [!TIP]
> You do not need a custom domain immediately. Resend provides `onboarding@resend.dev` out of the box for testing with your personal account email before verifying a domain. Users can opt out or customize their notification preferences in their account settings at any time.

## How the Free Tier Wake-Up Flow Works

```
                     ┌──────────────────────────────┐
                     │     User Opens Dashboard     │
                     └──────────────┬───────────────┘
                                    │
                                    ▼
                     ┌──────────────────────────────┐
                     │   GET /api/worker/wake       │ (Next.js serverless)
                     └──────────────┬───────────────┘
                                    │
                         wakeWorker() (Async HTTP Ping)
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ Render Free Tier Ingress: GET https://ballast-worker.onrender.com/health│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                 If sleeping, Render spins up container (~30-40s)
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                        Ballast Worker Awake                            │
│  - HTTP server answers 200 OK on /health                               │
│  - BullMQ workers poll Redis for pending briefs and actions            │
│  - Cron loop checks and executes scheduled briefs                      │
└────────────────────────────────────────────────────────────────────────┘
```

In addition to dashboard mount, whenever a user clicks **Regenerate Brief** or **Approve Action**, `enqueueBriefJob` and `enqueueActionJob` also fire `wakeWorker()` in the background to ensure immediate processing.

## Versioned Database Migrations

Ballast uses a numbered, version-tracked migration engine located in [`src/db/migrations/`](file:///home/jamesuchechi/Projects/Ballast/src/db/migrations):

* `001_init.sql`: Baseline schema creating all 14 tables, vector extension, and indexes.
* `002_add_source_inspection_and_metadata.sql`: Adds inspection columns (`sync_window_start`, `synced_at`, `fetched_at`, `last_error`, `raw_uri`, `meta`).
* `003_add_schedule_last_triggered_at.sql`: Adds `last_triggered_at` and supporting index for the cron engine.

### Concurrency Protection & Automation
1. **Advisory Locking**: When [`migrate()`](file:///home/jamesuchechi/Projects/Ballast/src/db/migrate.ts) executes, it acquires a PostgreSQL advisory lock (`pg_advisory_lock(7483920194)`). If Vercel and Render deploy concurrently, one process waits and proceeds safely without racing or colliding.
2. **Tracking Table**: Recorded migrations are tracked in `_migrations (id, filename, applied_at)`. Already-applied files are skipped.
3. **Automated on Every Deploy**:
   * **Render**: Configured in [`render.yaml`](file:///home/jamesuchechi/Projects/Ballast/render.yaml) as part of `buildCommand: npm install && npm run db:migrate`.
   * **Manual / Pre-deploy**: Run `npm run db:migrate` locally or in any deployment shell against production `DATABASE_URL`.

## Verifying Worker Operation

Once the Render service is deployed, check Render's live log stream:

1. **Startup Banner & HTTP Server**:
   ```text
   [Worker] Ballast async worker starting on queues "ballast-briefs" & "ballast-actions"...
   [Worker HTTP] Health & wake server listening on port 10000
   [Worker Env] Connecting with configurations:
     - DATABASE_URL: Configured
     - REDIS_URL: Configured
     - LLM Providers: Gemini=true, Groq=true, Mistral=true, OpenRouter=true
   ```
2. **Heartbeat**: Every 60 seconds:
   ```text
   [Worker Heartbeat] Ballast background worker alive (uptime: 60s, briefs: 0, actions: 0, schedules triggered: 0)
   ```
3. **Health Endpoint**:
   Visiting `https://<your-worker>.onrender.com/health` in your browser returns:
   ```json
   {
     "status": "ok",
     "uptimeSec": 124,
     "briefsProcessed": 0,
     "actionsProcessed": 0,
     "schedulesTriggered": 0,
     "timestamp": "2026-09-14T18:00:00.000Z"
   }
   ```
